Output files
============

A run that prints its numbers and exits leaves nothing to attach to a design review. Pass
``--outputs <dir>`` to either study command and the run leaves four files behind:

.. code-block:: bash

   cdadt size cases/b738.yaml --outputs b738_out
   cdadt optimize cases/b738_optimization.yaml --outputs b738_opt_out

.. list-table::
   :header-rows: 1
   :widths: 24 76

   * - File
     - What it is
   * - ``n2.html``
     - OpenMDAO's N2 diagram of the built model: every component, every connection, every
       solver. Generated from the live problem, so it is the model that was actually run rather
       than a drawing of one.
   * - ``trajectory.pdf``
     - What was flown, plotted against range -- one panel per quantity.
   * - ``report.txt``
     - The same text the command printed.
   * - ``results.json``
     - The same numbers as structured data. For an optimization this is the full record:
       baseline, optimum, and every constraint with its provenance, margin and status.

``--outputs`` and ``--json`` are independent; either, both or neither.

These four files are the whole output. OpenMDAO would otherwise scatter a ``reports/`` directory
beside whichever process happened to run it; :class:`~cdadt.blackbox.OpenConceptSizingBox` builds
its problem with ``reports=False``, so everything a study produces lands in the one directory the
caller named and nothing appears anywhere else. ``*_out/`` is in ``.gitignore``, since all four
files are regenerated by a single command.

What is plotted
---------------

The quantities, their units and their labels are the ones OpenConcept's own ``B738.py`` plots in
``show_outputs``, so the figure is comparable with the reference example rather than being a
second opinion about what matters:

.. list-table::
   :header-rows: 1
   :widths: 30 16 54

   * - Variable
     - Units
     - Panel
   * - ``fltcond|h``
     - ft
     - Altitude
   * - ``fltcond|Ueas``
     - kn
     - Equivalent airspeed
   * - ``fuel_burn_integ.fuel_burn``
     - lbm
     - Fuel burned
   * - ``throttle``
     - --
     - Throttle setting
   * - ``fltcond|vs``
     - ft/min
     - Vertical speed
   * - ``fltcond|M``
     - --
     - Mach number
   * - ``fltcond|CL``
     - --
     - Lift coefficient

All against ``range`` in nautical miles.

One difference from ``B738.py``, and it is only in where the number is read from: it plots
``fuel_used``, which is a promoted *input* of each phase and therefore not unambiguously readable
-- a promoted input name can address several components at once, which is why
:meth:`~cdadt.blackbox.OpenConceptSizingBox.readable` omits them. What the box publishes as an
output is each phase's fuel integrator, and each phase's carries on from the end of the one
before rather than restarting at zero. So the panel is cumulative mission fuel, the same curve
``B738.py`` draws.

That is an identity, not an observation: the response catalogue defines ``total_fuel`` as
``mission.loiter.fuel_burn_integ.fuel_burn_final`` -- the last node of the last phase of this very
trace -- and ``block_fuel`` as the same thing at the end of ``descent``. Both are therefore
readable straight off the panel. On the shipped case the trace runs from 179.31 lbm at the first
climb node, the takeoff roll already in it, to 41,000.07 lbm at the end of the loiter, which is
``total_fuel`` = 18,597.3177 kg.

The phases are discovered, and ordered by where they happen
-----------------------------------------------------------

Two questions, and neither is answered with a list of names.

**Which subsystems are phases.** A steady flight phase integrates its own state and so publishes
``ode_integ_phase.range_final``. The ground-roll phases -- ``v0v1``, ``v1vr``, ``rotate`` and the
rejected takeoff ``v1v0`` -- publish ``range`` but not that, so they are not part of the flown
trajectory. Keeping ``v1v0`` out matters: it retraces ground the aircraft has already covered,
and drawn on a range axis it is a trajectory that doubles back.

The discriminator is *published as an output*, which means
:meth:`~cdadt.blackbox.OpenConceptSizingBox.readable` and not
:meth:`~cdadt.blackbox.OpenConceptSizingBox.has`. The two disagree here, and only on the phases
this has to exclude: ``has`` falls back to ``get_val``, and ``v0v1``, ``v1vr`` and ``v1v0`` all
answer it for the marker while publishing no such output. A test holds that distinction, because
the failure it prevents is a plot that still looks like a plot.

**What order they are flown in.** Not alphabetical -- that puts loiter before the reserve climb.
Not the order the box lists them in either, since it publishes its outputs sorted by name. Phases
are ordered by the abscissa itself: where each one starts. For the shipped case that recovers
climb, cruise, descent, the three reserve phases, then loiter, and it is a fact read off the
converged mission rather than a convention written down here.

Nothing about those seven is written down in cdadt, which is the same reason the black box itself
is named in the case file rather than imported. A mission model with a second diversion, or
without a loiter, plots correctly with nothing changed here.

A quantity that only *some* phases publish is dropped from the figure rather than drawn with a
gap, because a trajectory drawn across a hole reads as a trajectory rather than as missing data.
Asking for one by name instead raises, naming the phase that does not publish it.

.. note::

   Read the trajectory off a **converged** box. Reading one mid-solve produces a plot of a state
   the solver was passing through, and nothing about the picture says so. The command line only
   writes artefacts after the run has converged; the classes will do as they are told.

From Python
-----------

.. code-block:: python

   from cdadt import Config, SizingAnalysis, StudyArtifacts

   analysis = SizingAnalysis(Config.from_yaml("cases/b738.yaml"))
   results = analysis.run()

   artifacts = StudyArtifacts("b738_out")
   artifacts.write_text(results.report(analysis.catalog), "report.txt")
   artifacts.write_json(results.to_dict(), "results.json")
   artifacts.write_n2(analysis.box)
   artifacts.write_trajectory(analysis.box, title="B738 design mission")

Matplotlib is an optional dependency, since only the trajectory plot needs it:

.. code-block:: bash

   pip install -e ".[plot]"

Without it, everything else still works and the plot raises an
:class:`~cdadt.artifacts.ArtifactError` naming the extra to install.
